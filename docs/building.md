# Building Lanes

Everything here runs on Windows 10 or 11, x64.

## What you need

| Tool | Why | Install |
| --- | --- | --- |
| **Rust** (via rustup) | The core. `rust-toolchain.toml` pins the exact compiler; rustup fetches it on first build | <https://rustup.rs> |
| **Visual Studio 2022 Build Tools**, "Desktop development with C++" workload (MSVC and a Windows SDK) | The Rust target is `x86_64-pc-windows-msvc`, which links with MSVC | `winget install Microsoft.VisualStudio.2022.BuildTools` and choose the workload |
| **.NET 10 SDK** | The window | `winget install Microsoft.DotNet.SDK.10` |
| **Inno Setup 6** | Only to build the installer | `winget install JRSoftware.InnoSetup` |

No administrator rights are needed to build or run Lanes; installing the build
tools themselves may ask for them.

## Building

```powershell
# Everything that ships, into dist\
powershell -ExecutionPolicy Bypass -File tools\build-release.ps1

# ... and the installer, into dist\installer\
powershell -ExecutionPolicy Bypass -File tools\build-installer.ps1
```

`build-release.ps1` builds the core with `cargo build --release`, publishes the
window self-contained and single-file with `dotnet publish`, and then **checks
that neither binary depends on the Visual C++ redistributable** - it fails the
build if one does. The core links the C runtime statically
(`.cargo/config.toml`) so that it runs on a clean Windows install.

Piece by piece:

```powershell
cargo build --release                 # target\release\Lanes.exe
cargo test --release                  # the core's unit tests
cargo clippy --all-targets --release  # lints; the code is kept warning-free
dotnet build ui-wpf -c Release        # the window; warnings are errors
```

Keep `Lanes.exe` and `Lanes.Window.exe` in the same folder: each finds the
other beside itself.

## Running a development build beside your installed Lanes

Only one Lanes normally runs at a time, and two copies managing the same
applications would undo each other's changes endlessly. For development there
is a safe way to run a build beside an installed Lanes:

1. Copy `Lanes.exe` and `Lanes.Window.exe` into a folder of their own.
2. Put an empty `portable.txt` beside them. The copy now keeps all its state in
   a `Lanes` folder there, never touching the installed copy's.
3. Put a `test-apps.txt` beside them listing, one per line, the executables this
   copy may change - for example a small player you use only for testing. **It
   changes nothing else**, whatever its rules say, and never touches Windows'
   default device or volumes. With no file, it changes nothing at all.
4. Start it with the environment variable `LANES_SEPARATE_INSTANCE=1`:

   ```powershell
   $env:LANES_SEPARATE_INSTANCE = "1"; .\Lanes.exe
   ```

Its windows and tray tooltip say "(test copy)", and it has its own taskbar
identity. **Quit it when you are done** (tray > Settings > Quit Lanes): a
forgotten test copy is easy to mistake for the real one.

The variable does nothing without `portable.txt`, so an installed Lanes can
never be made to run twice.

## Regenerating the icon

```powershell
powershell -ExecutionPolicy Bypass -File tools\make_icon.ps1
```

Draws the mark and writes `assets\icon.ico`, `icon.png`, `tray.png` and the raw
`tray-32.rgba` the tray icon is compiled from. The outputs are committed, so
building never needs this.

## Releases

Releases are built by GitHub Actions from a version tag (`.github/workflows/`),
so what is published is built from the public source. See
[code-signing.md](code-signing.md) for how releases are signed.

## Making your own version

Lanes is GPL-3.0-or-later: you may change it and share your version under the
same licence. If you distribute a fork under another name, change these so it
does not collide with an installed Lanes:

| What | Where |
| --- | --- |
| The state folder name | `core/src/paths.rs`, `APP_FOLDER` |
| The single-instance lock | `core/src/instance.rs`, `MUTEX_NAME` |
| The start-on-boot registry value | `core/src/autostart.rs`, `VALUE_NAME` |
| The taskbar identity | `ui-wpf/Api/CoreProcess.cs`, and `AppUserId` in `installer/Lanes.iss` |
| The installer's `AppId`, names and URL | `installer/Lanes.iss` |
| Where the window looks for state | `ui-wpf/Api/CoreClient.cs` |

## Conventions

- **Explain why, not what.** Comments and docs say why the code is the way it is
  - especially where the obvious approach fails silently. Every public item has
  a doc comment.
- **Verify by result.** Much of Windows audio reports success while doing
  nothing. Read values back; listen.
- **One owner of the config**, the core thread. Nothing else loads, changes and
  saves it.
- **Nothing is changed that the user did not ask for.** Channels ship empty,
  hotkeys ship empty, and the window never rearranges itself.
- When behaviour changes, its documentation changes in the same commit.
